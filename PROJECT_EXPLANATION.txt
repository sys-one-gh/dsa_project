E-COMMERCE INVENTORY & ORDER PROCESSING ENGINE — FULL PROJECT EXPLANATION
===========================================================================

1. WHAT THIS PROJECT IS
---------------------------------------------------------------------------
- A console-based Python backend simulating a simplified e-commerce system.
- Not a real store — no UI, no persistence, no payment processing.
- Built to prove correct, meaningful use of six data structures and four
  GoF (Gang of Four) design patterns inside ONE connected system.
- Domain flow it models: catalogue -> cart -> checkout -> order queue.
- Everything resets when the program exits (all state lives in memory).

2. WHY IT'S STRUCTURED THIS WAY
---------------------------------------------------------------------------
- Each data structure was picked because it's the natural fit for the
  operation, not forced in artificially:
  - Dictionary  -> O(1) SKU lookup for the catalogue.
  - HashSet     -> tag membership + fast set math (union/intersection).
  - Custom linked list -> cart items, so add/remove is a pointer op.
  - Sorted linked list -> keeps "browse by price" always sorted, no re-sort.
  - Stack (x2)  -> undo/redo history, LIFO order is exactly what "undo" needs.
  - Queue (FIFO) -> orders must be fulfilled in the order they were placed.
- Each design pattern solves a specific flexibility problem:
  - Factory Method -> hides which Product subclass to instantiate.
  - Decorator      -> lets discounts stack in any combination, at runtime.
  - Command        -> turns cart edits into objects so they can be undone.
  - Facade         -> hides shipping's multi-step calculation behind one call.

3. FILE-BY-FILE BREAKDOWN
---------------------------------------------------------------------------

3.1 models.py — Product hierarchy + Factory Method
  - Product (ABC): base class, holds sku, name, price, tags (a set).
  - calculate_tax() is abstract — every subclass MUST define its own tax rule.
  - get_weight() defaults to 0.0 — only PhysicalProduct overrides it.
  - PhysicalProduct: has a weight attribute, tax = 13% of price.
  - DigitalProduct: no weight, tax = 5% of price (lower than physical).
  - SubscriptionProduct: no weight, tax = 0% (subscriptions untaxed here).
  - ProductFactory.create_product(type, sku, name, price, tags, weight):
    - Reads a string ("Physical"/"Digital"/"Subscription"), returns the
      correct subclass instance.
    - Raises ValueError on an unknown type string.
    - This is the Factory Method pattern: callers never call a subclass
      constructor directly, they just say "give me a Physical product."

3.2 catalogue.py — Inventory storage, CRUD, search, sorted browsing
  - SortedNode / SortedLinkedList:
    - A singly linked list kept sorted ascending by product.price.
    - insert() walks the list once to find the correct position — O(n)
      insert, but browsing is always pre-sorted (no sort-on-read cost).
    - remove(sku) unlinks a node by SKU (used when a product is deleted
      or its price changes and needs to move position).
    - to_list() flattens the linked list into a Python list for display.
  - Catalogue class:
    - self.products: Dict[str, Product] — the CRUD store, keyed by SKU.
    - self.sorted_list: SortedLinkedList — kept in sync with the dict.
    - add_product(product) = CREATE. Raises ValueError on duplicate SKU.
    - get_product(sku) = READ. Returns None if not found.
    - update_product(sku, **fields) = UPDATE. Only overwrites fields that
      were actually passed. If price changed, it removes and re-inserts
      the node in sorted_list so ordering stays correct.
    - remove_product(sku) = DELETE. Removes from both the dict and the
      sorted linked list. Raises KeyError if the SKU doesn't exist.
    - search_by_keyword(keyword) — case-insensitive substring match on
      product name. Returns a List[Product].
    - search_by_tags(tags, match_all) — the "set operations" requirement:
      - match_all=True  -> tags.issubset(p.tags)  (INTERSECTION logic —
        product must have ALL requested tags).
      - match_all=False -> tags & p.tags           (ANY-match — product
        must share AT LEAST ONE tag).
    - all_tags() — unions every product's tag set into one master set
      (demonstrates the UNION set operation explicitly).

3.3 cart.py — Custom linked-list cart + Command pattern for undo/redo
  - CartItem: a node holding (product, quantity, next-pointer).
  - ShoppingCartList: the custom linked list itself.
    - add(product, qty): if the SKU already exists in the list, just bumps
      its quantity; otherwise inserts a new node at the head (O(1)).
    - remove(sku, qty=None): removes `qty` units, or the whole node if
      qty is None or >= current quantity. Walks the list with a
      prev/current pair so it can unlink safely.
    - update_quantity(sku, new_qty): sets quantity directly; if new_qty
      drops to 0 or below, the node is removed entirely.
    - get_subtotal(): traverses the whole list, sums price * quantity.
    - to_list(): flattens nodes into a Python List[CartItem] for display.
  - ICartCommand (ABC): defines execute() and undo() — the Command
    pattern's core contract.
  - AddItemCommand: execute() adds qty to cart; undo() removes that exact
    qty back out.
  - RemoveItemCommand: execute() removes qty (or all) from cart, but first
    SAVES what it actually removed (product + amount) so undo() can add
    it back precisely, even if less was available than requested.
  - UpdateQuantityCommand: execute() sets a new quantity but first records
    the OLD quantity, so undo() can restore it exactly.
  - CartManager: the piece that makes undo/redo work.
    - undo_stack / redo_stack: plain Python lists used AS stacks
      (append = push, pop = pop) — this is the "two Stacks" requirement.
    - execute_command(cmd): runs cmd.execute(), pushes cmd onto
      undo_stack, and CLEARS redo_stack (standard undo/redo rule — once
      you make a new edit, the old "redo" future is invalidated).
    - undo(): pops the last command off undo_stack, calls its undo(),
      pushes it onto redo_stack. Returns False if there's nothing to undo.
    - redo(): pops off redo_stack, re-runs execute(), pushes back onto
      undo_stack. Returns False if there's nothing to redo.

3.4 discounts.py — Decorator pattern for stacking discounts
  - IOrder (ABC): just one method, get_total().
  - BaseOrder: wraps the raw cart subtotal — the innermost, undecorated
    order. get_total() just returns that subtotal.
  - DiscountDecorator (ABC): wraps ANOTHER IOrder (self.order) — this is
    what lets decorators be layered on top of each other.
  - FlatDiscount(order, amount): subtracts a flat dollar amount from
    whatever total the wrapped order produces. Floors at 0 (never negative).
  - PercentageDiscount(order, percentage): multiplies the wrapped total by
    (1 - percentage). e.g. percentage=0.10 takes 10% off.
  - BuyOneGetOneFree(order, item_prices): given a list of individual unit
    prices in the cart, subtracts the price of the CHEAPEST unit (i.e.
    that unit becomes "free") — only if there are 2+ units total.
  - Because each decorator wraps an IOrder and IS an IOrder, they can be
    chained in any order and any combination:
      PercentageDiscount(FlatDiscount(BaseOrder(1040), 50), 0.10)
      -> (1040 - 50) * 0.90 = 891.00
    Each layer only knows about the layer directly inside it — that's the
    whole point of the Decorator pattern (no giant if/else discount logic).

3.5 shipping.py — Facade pattern for shipping cost
  - ShippingFacade exposes ONE public method: calculate_shipping(cart, zone).
  - Internally it hides three separate steps behind that single call:
    1. _calculate_weight(cart): sums product.get_weight() * quantity for
       every item in the cart (digital/subscription products contribute
       0 automatically, since get_weight() defaults to 0.0).
    2. _lookup_zone_multiplier(zone): looks up "domestic" (1.0x) vs
       "international" (1.5x) in a dict, defaulting to 1.0x for unknown
       zones.
    3. _carrier_quote(weight, multiplier): a STUB standing in for what
       would be a real carrier API call — computes
       (base_rate + weight * rate_per_kg) * multiplier.
  - The caller (main.py) never sees any of steps 1-3 — it just calls
    ShippingFacade.calculate_shipping(cart, "Domestic") and gets a number.
    That's the Facade pattern: a simple front door over a more complex
    subsystem.

3.6 orders.py — FIFO order queue
  - Order class: order_id (auto-incrementing), items (List[str] of SKUs),
    final_total, and a status string ("Pending" -> "Fulfilled").
  - OrderProcessor:
    - order_queue: a collections.deque used strictly FIFO (append on the
      right, popleft from the left) — this is the "Queue<Order>"
      requirement.
    - order_history: List[Order] — every order that has been fully
      processed ends up here (a second, explicit use of a plain List).
    - submit_order(order): pushes an order onto the queue, prints a
      confirmation.
    - process_orders(): drains the ENTIRE queue in order, marking each
      order "Fulfilled" and moving it into order_history as it goes.

3.7 main.py — the interactive console app that ties everything together
  - Seeds the catalogue with 4 sample products on startup (Laptop, Python
    Guide e-book, Music Premium subscription, Headphones) so there's
    something to search/cart immediately.
  - Runs a loop that prints a numbered menu and reads a choice via input().
  - Menu options map directly onto the modules above:
    1  Add Product      -> ProductFactory + Catalogue.add_product (CREATE)
    2  Update Product   -> Catalogue.update_product (UPDATE)
    3  Delete Product   -> Catalogue.remove_product (DELETE)
    4  Browse by price  -> Catalogue.sorted_list.to_list() (READ, sorted)
    5  Keyword search    -> Catalogue.search_by_keyword
    6  Tag search        -> Catalogue.search_by_tags (all/any modes)
    7  Add to cart       -> CartManager.execute_command(AddItemCommand)
    8  Remove from cart  -> CartManager.execute_command(RemoveItemCommand)
    9  Update quantity   -> CartManager.execute_command(UpdateQuantityCommand)
    10 View cart         -> ShoppingCartList.to_list() + get_subtotal()
    11 Undo              -> CartManager.undo()
    12 Redo              -> CartManager.redo()
    13 Checkout          -> builds BaseOrder, optionally wraps it in
                             FlatDiscount / PercentageDiscount /
                             BuyOneGetOneFree, calls ShippingFacade, then
                             on confirmation creates an Order and calls
                             OrderProcessor.submit_order(); clears the cart
                             and wipes the undo/redo stacks (fresh start).
    14 Process queue     -> OrderProcessor.process_orders()
    0  Exit              -> breaks the loop.
  - Every prompt uses an ask(prompt, default) helper: pressing Enter
    accepts the bracketed default, or the user can type a custom value —
    so the whole program is genuinely interactive, not hardcoded.

4. TEST SUITE (tests/ folder) — what each test file is FOR
---------------------------------------------------------------------------
  - Purpose overall: prove every module works correctly in isolation
    (unit tests) before trusting main.py to wire them together. Also
    satisfies the rubric's "minimum 10 test cases" requirement — this
    suite has 39, spread across one file per module so a grader can see
    each module was tested on its own merits.
  - Framework: Python's built-in `unittest` (no extra install needed).
  - tests/__init__.py — empty file, exists only so `unittest discover`
    treats tests/ as an importable package. Not a test file itself.

  4.1 test_models.py — tests models.py (Product classes + Factory)
    - test_creates_physical_product   — factory("Physical") returns a
                                         PhysicalProduct with weight set.
    - test_creates_digital_product    — factory("Digital") returns a
                                         DigitalProduct.
    - test_creates_subscription_product — factory("Subscription") returns
                                         a SubscriptionProduct.
    - test_invalid_type_raises        — an unrecognized type string raises
                                         ValueError instead of failing silently.
    - test_physical_product_tax       — confirms 13% tax rate on physical goods.
    - test_digital_product_tax        — confirms 5% tax rate on digital goods.
    - test_subscription_product_tax_is_zero — confirms subscriptions are untaxed.
    - test_digital_product_weight_is_zero — confirms get_weight() defaults
                                         to 0.0 for non-physical products.

  4.2 test_catalogue.py — tests catalogue.py (Dictionary CRUD + sorted list + search)
    - test_add_and_get_product        — CREATE then READ returns the same product.
    - test_duplicate_sku_raises       — adding a SKU that already exists is rejected.
    - test_update_product_price_resorts_list — UPDATE-ing a price moves the
                                         product to the correct spot in the
                                         price-sorted linked list.
    - test_remove_product             — DELETE removes it from both the dict
                                         AND the sorted linked list.
    - test_remove_missing_product_raises — deleting an unknown SKU raises KeyError.
    - test_search_by_keyword          — substring match on product name works.
    - test_search_by_tags_match_all   — intersection-style tag search (product
                                         must have ALL given tags).
    - test_search_by_tags_match_any   — union-style tag search (product needs
                                         only ONE matching tag).
    - test_sorted_list_ascending_order — the sorted linked list is always in
                                         non-decreasing price order.

  4.3 test_cart.py — tests cart.py (linked-list cart + Command undo/redo)
    - test_add_item_increases_subtotal — adding a product raises the subtotal
                                         by the expected amount.
    - test_add_same_sku_merges_quantity — adding the same SKU twice merges
                                         into one node instead of duplicating it.
    - test_remove_partial_quantity    — removing fewer units than are in the
                                         cart just decrements the quantity.
    - test_remove_all_deletes_node    — removing all (or more than) the
                                         quantity deletes the node entirely.
    - test_update_quantity            — directly setting a new quantity works.
    - test_undo_redo_add_item         — undo() reverses an AddItemCommand,
                                         redo() re-applies it, subtotal matches
                                         at every step.
    - test_new_command_clears_redo_stack — running a new command after an
                                         undo wipes the redo stack (you can't
                                         redo into a future that no longer exists).
    - test_undo_remove_item_restores_it — undoing a RemoveItemCommand puts the
                                         exact removed quantity back.
    - test_undo_update_quantity_restores_previous_value — undoing an
                                         UpdateQuantityCommand restores the
                                         quantity that existed before the update.
    - test_undo_on_empty_stack_returns_false — calling undo() with nothing to
                                         undo returns False instead of crashing.

  4.4 test_discounts.py — tests discounts.py (Decorator pattern)
    - test_flat_discount               — a flat $ discount subtracts correctly.
    - test_flat_discount_does_not_go_negative — a discount larger than the
                                         total floors at $0, never negative.
    - test_percentage_discount         — a % discount multiplies correctly.
    - test_stacked_discounts_apply_in_order — a FlatDiscount wrapped in a
                                         PercentageDiscount applies both, in
                                         the correct nested order (flat first,
                                         then percentage off the reduced total).
    - test_bogo_removes_cheapest_item  — Buy-One-Get-One-Free subtracts the
                                         cheapest unit's price when 2+ units exist.
    - test_bogo_no_effect_with_single_item — BOGO does nothing when there's
                                         only 1 unit (nothing to give free).

  4.5 test_shipping.py — tests shipping.py (Facade pattern)
    - test_domestic_shipping_cost      — base rate + weight-based cost comes
                                         out correct for a domestic order.
    - test_international_shipping_costs_more — the same cart costs more to
                                         ship internationally (1.5x multiplier).
    - test_digital_products_add_no_weight — digital items contribute 0kg, so
                                         shipping cost is just the base rate.

  4.6 test_orders.py — tests orders.py (FIFO Queue)
    - test_orders_processed_in_fifo_order — orders come out of the queue in
                                         the exact order they were submitted.
    - test_process_orders_marks_fulfilled — processing an order flips its
                                         status from "Pending" to "Fulfilled".
    - test_queue_empty_after_processing — the queue is empty once every
                                         order has been processed.

  4.7 Running the tests
    - Whole suite:        python3 -m unittest discover -s tests -t .
    - One file:            python3 -m unittest tests.test_cart
    - One test method:     python3 -m unittest tests.test_cart.TestCommandUndoRedo.test_undo_redo_add_item
    - Verbose output:      add -v to any of the commands above.

5. HOW A FULL USER JOURNEY FLOWS THROUGH THE CODE
---------------------------------------------------------------------------
  1. User launches main.py -> seed_catalogue() populates 4 products.
  2. User searches/browses -> hits Catalogue methods, reads Dict + sorted
     linked list.
  3. User adds items to cart -> AddItemCommand pushed onto undo_stack,
     ShoppingCartList linked list grows.
  4. User undoes a mistake -> CartManager.undo() pops the stack, reverses
     the last command, pushes it onto redo_stack.
  5. User checks out -> subtotal wrapped in BaseOrder, optionally layered
     with discount decorators, shipping computed via ShippingFacade.
  6. User confirms -> a new Order object is built and pushed onto
     OrderProcessor's deque (the FIFO queue); cart is cleared.
  7. User processes the queue -> every pending Order is dequeued in the
     order it was submitted, marked Fulfilled, and archived into
     order_history.

8. WHAT'S DELIBERATELY OUT OF SCOPE
---------------------------------------------------------------------------
  - No database or file persistence — everything lives in memory and is
    lost when the program exits.
  - No real payment processing or carrier API — ShippingFacade's carrier
    call is a stub, not a live integration.
  - No authentication/multi-user support — this is a single-session demo.
  - UML class diagram, technical report, and git/task-board evidence are
    separate deliverables required by the grading rubric, not part of the
    code itself (see README.md's Marking Scheme section).
